## 1. MEDIUM: snapshots use the session's copy of `region`, which is `updatable = false`, so a stale save versions the old region
- **Where:** `HistoryWriter.java:107-111`. The snapshot is taken from `s.get(liveType, id)`, the object the session already holds. `region_id` is mapped `updatable = false` (F3) on `Payment.java:54`, `PaymentPromise.java:98` and `Dispute.java:67`, and those entities have no `@Version`.
- **Failure:** a transaction or open-in-view session loads a promise, payment or dispute. A region move commits meanwhile (native SQL plus `touch`, as BE-08 does). The first transaction then saves the record.
  - The ORM correctly keeps the new `region_id` in the row (F3).
  - The writer snapshots the in-memory object, so the new version records the **old** region from `t` onward.
- **Probe `p1_staleRegionOnAPromiseSavedAfterAMove`:** `live region=2 open version region=1`, and `check()` gives `[drifted PROMISE 1]`.
- **Consequences:** B3 "region at the time" is wrong for every as-of read after such a save. BE-08's required case "a stale `PaymentPromise` saved after the move keeps the new region" (§8.3) will fail `historyIsInStep`.
- **Fix:** before snapshotting, re-read the non-updatable columns of the keys being versioned. Either run one batched `select e.id, e.region.id from <L> e where e.id in :ids` per chunk and override `regionId` on the snapshot, or `s.refresh(live)` the rows (safe here, since the flush has already run). Add the probe as a test.

## 2. MEDIUM: provenance other than USER is never tested
- **Where:** `HistoryWriter.java:76-77, 89-95` (`originRef`, `WriteOrigins.actor`).
- **The gap:** every history test asserts `origin == "USER"` and `originRefId == null` (`HistoryCaptureTest.java:606-616`). No test covers:
  - the AUTOMATION → `ruleId` or APPROVAL → `pendingChangeId` mapping;
  - an actor taken from a bound origin (`withActor`, the D4/CF-1 rule "provenance must still be bound when the transaction commits");
  - the SYSTEM origin with a null actor for background work.
- The sweep case (`HistoryCaptureTest.java:390-401`) runs on the test thread as admin and asserts `USER`. The production sweep has no principal and writes `SYSTEM`.
- **Why it matters:** §8.4 requires each capture case to assert origin, actor and `txId`. Swapping the two refs, or reading the actor from `currentUser` instead of `WriteOrigins.actor`, would pass the whole suite.
- **Probe `p3_boundOriginsAreStamped`:** the code works today. It gave `APPROVAL ref=77 actor=<maker>` and `SYSTEM ref=null actor=null`.
- **Fix:** add a capture case under `WriteOrigins.callWith(WriteOrigin.approval(pc, checker).withActor(maker), () -> tx.execute(...))`, one under `WriteOrigin.automation(...)`, and a sweep with the SecurityContext cleared that asserts `SYSTEM` with a null actor.

## 3. LOW: `HistoryTracker.touch` cannot handle a held row that SQL has deleted; the whole transaction rolls back
- **Where:** `HistoryTracker.java:52-60`. The code calls `em.refresh(held, …)` and catches `EntityNotFoundException`, then detaches the row.
- **The problem:** in Hibernate 6.5.3, `SessionImpl.refresh` converts the `UnresolvableObjectException` through `ExceptionConverterImpl.rollbackIfNecessary` (ExceptionConverterImpl:135-138, 258-270). That marks the transaction rollback-only before the catch runs. So the "a vanished row is detached" branch cannot work.
- **Probe `p2_touchOfAHeldRowDeletedBySql`:** `UnexpectedRollbackException: Transaction silently rolled back because it has been marked as rollback-only`, and the row is still there.
- **Reach:** no caller hits this today (BE-08 reconcile runs in a fresh session). It is the sanctioned API, though, and its contract promises this case.
- **Fix:** look up which of the ids still exist with one query first. Detach the held copies of the missing ids without calling `refresh`, and refresh only the rows that exist.

## 4. LOW: `HistoryReconciler.check()` joins the caller's transaction and calls `em.clear()`
- **Where:** `HistoryReconciler.java:32-36, 86, 124`.
- **The problem:** the read-only `TransactionTemplate` has the default propagation, REQUIRED. Called inside an active transaction, it participates in it (the read-only flag is ignored). `em.clear()` after every chunk then silently discards the caller's unflushed changes and detaches its entities.
- **Reach:** latent. BE-08's `reconcile()` and `POST /api/admin/history/reconcile` will call it.
- **Fix:** use `PROPAGATION_REQUIRES_NEW`.

## 5. LOW: two risky branches are never run by any test
- The lock-and-recheck branch (`HistoryWriter.java:122-128`, CHILD without UPDATED) has no test. No current write path reaches it: invoice lines only change together with an invoice UPDATE.
- `HistoryTracker.touch(…, lock = true)` has no test. It is the refresh or `find` with `PESSIMISTIC_WRITE` (`HistoryTracker.java:54-56`) that BE-08's reconcile relies on.
- The refresh-a-stale-held-copy branch has no test either. That is the deviation the log calls necessary. `HistoryTestSupport.touch` always runs in a fresh session, so `held` is always null.
- Removing any of these branches leaves the suite green.
