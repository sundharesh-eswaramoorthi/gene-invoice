## Findings

### 1. (medium) An editor who holds no region grants is treated as "unbounded", so the grants editor offers everything and the new-user pre-fill is refused
- `F/features/users/region_grants_editor.dart:124`: `bool get unbounded => editor.regions.isEmpty;`. With this, `covers`, `offersLevel` and `offersAllRecords` all return true. `addable` (line 197) offers every active region. `initialGrantsFor` (line 89) pre-fills DEFAULT at the role's full level with scope ALL.
- The comment says this is for a server that does not yet report regions. Since BE-02, however, `/me` always sends `regions`, and for a staff user with no grants it is `[]`. That state is legitimate:
  - USER_MANAGE is global (§4.1).
  - §4.6 explicitly allows a user "left deliberately with no grants".
- Failure scenario: a user administrator whose role has USER_MANAGE but who holds no region grant opens New user and picks a CASHIER role.
  - The editor pre-fills `{DEFAULT, MANAGE, ALL}`, offers every region at READ, MANAGE and APPROVE, and `users_screen.dart:203` always sends it.
  - From BE-05, `POST /api/users` answers 403 ("each row is bounded by the caller's own grant"), so the user cannot be created until the admin notices and removes the row by hand.
  - On the Regions tab of an existing user, every row shows as editable, and every save 403s.
- This breaks the slice gotcha "the grants editor never offers more than the editor holds".
- Fix: decide unbounded from "the server did not report regions" (for example a nullable `regions` or a parsed-presence flag on `CurrentUser`), not from `regions.isEmpty` for staff. Then add a test with a `regions: []` staff editor.

### 2. (low) APPROVE is offered, and pre-filled, without CHANGE_APPROVE
- `GrantBounds.offersLevel` (`region_grants_editor.dart:140`) and `initialGrantsFor` bound APPROVE by the editor's own level only.
- From BE-13, §4.6 also requires CHANGE_APPROVE in the region to grant APPROVE. `levelRoleNeeds` returns APPROVE for any role holding CHANGE_APPROVE or APPROVAL_THRESHOLD_MANAGE (for example ADMIN).
- Failure scenario: an editor at APPROVE level whose role lacks CHANGE_APPROVE creates an ADMIN-role user. APPROVE is pre-filled and sent, and the server answers 403.
- This is a recorded deviation, and the server stays authoritative. It is a one-line guard: `editor.hasIn(Privileges.changeApprove, regionId)` for the APPROVE segment and the pre-fill cap.

### 3. (low) The customer create dialog pre-selects the default region, so the "required" Region choice is never actually required
- `F/features/customers/customers_screen.dart:343-360` (`_seedRegion`): with several choices and no single region in view, it pre-selects the default region. The validator at `:396` can therefore never fire unless the default region is not a choice.
- §7.5 and §6.4 intend an explicit choice: the server answers 400 "Choose the region this customer belongs to" rather than guess.
- Failure scenario: a user who manages NORTH (the default) and SOUTH, viewing all regions, fills in the form and saves. The customer silently lands in NORTH.
- This is a UX and spec divergence, not a data leak.

### 4. (low) The move sends `version` only when present, and against §6.5 and today's backend it never is; the test invents the field
- `F/features/customers/move_region_dialog.dart:128` has `if (c.version != null) 'version': c.version`. However, `CustomerDto` (§6.5, and `backend/.../customer/CustomerDtos.java:17-30`) has no `version`. The real request therefore never carries it, and the stale-page check in §5.6.8 step 6 (`req.version != null`) never runs. A move made from a stale page proceeds with no 409.
- `FT/detail_gating_test.dart:89` fixtures `'version': 4` and asserts it in the POST body (`:323`). That exercises a path the contract cannot produce.
- This is mostly a design-contract gap: §6.4 asks for a `version` that §6.5 never exposes. Flag it to the backend stream (add `version` to `CustomerDto`), or record it as a known gap.
