## Medium

### M1. Switching the approvals view keeps the current page number
- **Where:** `frontend/lib/features/approvals/approvals_screen.dart:77` (`onSelectionChanged: (s) => setState(() => _view = s.first)`) and `:51` (`extraParams: {'view': view.name}`).
- **Problem:**
  - Every other change to the list resets the page to 0 (`TableQuery.withSort`/`withSize`/filters, `table_models.dart:63-66`). A view change only swaps `extraParams`, so `widget.query.page` stays where it was.
  - `DataTableScaffold.didUpdateWidget` (`data_table_scaffold.dart:154-158`) also clears the selection only when `query` changes, not when `extraParams` do.
- **Scenario:** an approver is on page 3 of "All I can see" (`?page=2`) and switches to "Awaiting my approval", which has 5 rows. The request is `view=AWAITING_ME&page=2`, the server returns an empty page, and the screen says "Nothing is waiting for your approval" although 5 changes are waiting.
- **Fix:** on a view change, push `widget.query.copyWith(page: 0)` through `RouteQuery`. Alternatively, put `view` in the URL so that it is part of the query.

### M2. Changing region while a thresholds save is in flight leaves a permanent spinner
- **Where:** `frontend/lib/features/approvals/approval_thresholds_screen.dart:174-185`, `:113-123`, `:395-396` and `:191`.
- **Problem:**
  - Only the Save button is disabled while `_saving`. The region dropdown's `onChanged` stays live (`:182-184`).
  - `_selectRegion` switches `_regionId` and loads the new region.
  - When the earlier PUT then completes, `_save` does `setState(() => _seed(saved, ...))` without checking that `saved.regionId == _regionId`.
- **Scenario:**
  1. The user edits South and clicks Save.
  2. While the PUT is pending, they pick North, and North's GET returns first.
  3. South's PUT response then overwrites `_loaded` and the drafts.
  4. `build` now sees `loaded.regionId (South) != regionId (North)` (`:191`). It shows `LinearProgressIndicator` indefinitely with no rows and no Save, until the user picks another region.
  5. On a 202, the "needs a second approver" snack also appears over North.
- **Fix:** guard the post-PUT seed with `if (saved.regionId != _regionId) return;`, or disable the dropdown while `_saving`.

## Low

### L1. A 202 that lacks a usable `pendingChange` is reported as saved, or as a failure
- **Where:** `approval_thresholds_screen.dart:394-417`.
- **Problem:**
  - `held = res.statusCode == 202 ? saved.pendingChange : null`. If the 202 has no `pendingChange` map, the else branch shows "Approval thresholds saved" for a held loosening. FE-05's goal is that no save ever announces "saved" for a held change.
  - If `pendingChange` is present but has no numeric `id`, `PendingChangeBrief.fromJson` (`approval_models.dart:105`, `(json['id'] as num)`) throws inside the try. The catch then shows an error snack for a PUT that did apply its tightening rows, and the form is not re-seeded.
- **Note:** §6.11 promises both fields, so this is defensive only.
- **Fix:** branch on `statusCode == 202` first, and fall back to the `Location` header for the id.

### L2. The chosen view is lost on every trip to a change and back
- **Where:** `approvals_screen.dart:35,42`; the back links in `approval_detail_screen.dart:45,52`.
- **Problem:** `_view` lives only in widget state. Opening a row (`context.go('/approvals/{id}')`) and returning (`goGuarded(context, '/approvals')`) builds a new `ApprovalsScreen`, so the view resets to AWAITING_ME. An approver working through "All I can see" or "My requests" is thrown back to the default each time.
- **Fix:** keep `view` in the route query.

### L3. THRESHOLD_CHANGE links and the thresholds screen depend on REGION_VIEW
- **Where:** `approval_models.dart:49` (`'REGION' => '/regions/$id'`); `router.dart:252-254` (`/regions/:id` needs `regionView`); the only link to `/approval-thresholds` is `region_detail_screen.dart:54`.
- **Problem:** the `/approval-thresholds` route admits `changeApprove` or `approvalThresholdManage` holders (`router.dart:238`). A role holding those privileges without REGION_VIEW is sent to `/` when it clicks a threshold change's "Record" link. It also has no in-app way to reach the thresholds screen.
- **Fix:** link REGION rows to `/approval-thresholds?regionId=N`. Add an entry point from the approvals screen for holders of either privilege.

### L4. The approvals routes admit customer logins, and the detail's Back lands on a 403
- **Where:** `router.dart:216-232` (`needs(navPrivilegesFor('/approvals'))`, and `needs()` at `:53-57` ignores `hideForCustomer`); `approval_detail_screen.dart:45,52`.
- **Scenario:**
  1. A customer login holding INVOICE_VIEW clicks View on an invoice's pending banner.
  2. The detail page opens, which is correct since the server redacts it.
  3. Back goes to `/approvals`, and the list GET is 403 for customers (§6.11), so the page shows an error.
- **Note:** this is harmless for security, because the server refuses the request.
- **Fix:** for a customer login, send Back to the record (`recordRoute`), and redirect customers away from `/approvals`.
