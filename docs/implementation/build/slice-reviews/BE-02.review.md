## Findings (most severe first)

### 1. HIGH: a customer login is no longer confined to its own customer on update, cancel, delete and preview paths (cross-customer writes)
- **Location:**
  - `B/poc/ScopeResolver.java:213-214`: `requireVisible` does `if (currentUser.isCustomer()) return;`.
  - Callers that relied on the old `requireInBook` for ownership:
    - `B/customer/CustomerService.java:265` (update), `:314` (delete)
    - `B/invoice/InvoiceService.java:116` (update), `:359` (cancel), `:218-220` (previewDueDate)
    - `B/payment/PaymentService.java:117` (update)
- **What changed:**
  - Before BE-02, `requireInBook(id)` ran `inScope(..., forX().predicates())`. For a customer login that predicate is `customer.id = own`, so another customer's record gave 404 (AUTH-08).
  - `requireVisible` now returns at once for customer logins. §5.6.4 says "callers keep today's own-customer checks", but these callers had no explicit check; their only ownership check was the predicate that has now been removed.
  - `get()` paths still have their explicit own-customer check. The write paths above do not.
- **Proof:**
  - The CUSTOMER role is editable through `PUT /api/roles/{id}`, and it is already seeded with a MANAGE privilege (`DOCUMENT_MANAGE`, `DataSeeder:96`). Give it `INVOICE_MANAGE` and `CUSTOMER_MANAGE`.
  - A customer login for "Mine Ltd" then runs `PUT /api/customers/{Other Ltd}` and gets **200**; the other customer is renamed.
  - It also runs `POST /api/invoices/{Other Ltd's invoice}/cancel` and gets **200**; the invoice is CANCELLED.
  - On the BE-01 snapshot, both calls give **404**.
  - `DELETE /api/customers/{id}` and `PATCH /api/payments/{id}` follow the same path.
- **Fix:** In `requireVisible`, for a customer login, check ownership instead of returning. For example:
  - `if (!queryExecutor.inScope(kind.type, kind.schema, id, List.of(ownPredicate(kind, me.getCustomerId())))) throw new NotFoundException(nf)`,
  - or compare the record's customer id with `customerIdOrNull()`.
  - Add a customer-login case for each write path.

### 2. LOW: the new region scoping of disputes, payments and promises has no test
- **Location:** `T/auth/PrincipalRightsTest.java`. The only by-id region cases are customers, invoices and `/payments/credits`, and the only list cases are customers and invoices.
- **Detail:**
  - The slice changes staff dispute visibility (the LOG says "Staff now see disputes only in regions where they hold a grant"): `DisputeController.list`, export and `DisputeService.get` now go through the region predicate.
  - Nothing tests that a dispute, payment or promise in an ungranted region is absent from its list and gives 404 by id, or that `regionIds` narrows those lists.
  - A mistake in the `Kind.DISPUTE`, `PAYMENT` or `PROMISE` predicates or tiers would pass the suite. BE-03's `RegionBookTest` is meant to cover the read side, so this is a gap until then, not a missing acceptance item.
- **Fix:** Add one list-plus-by-id case per kind to `PrincipalRightsTest`.

### 3. LOW: the bridge grant is not atomic with the user it belongs to
- **Location:** `B/user/UserController.java:155-158`. The controller has no `@Transactional`.
- **Detail:**
  - `userRepository.save(u)` commits in its own transaction. `regionGrantService.ensure(...)` then runs in a second one.
  - If `ensure` or `defaultRegion()` fails (for example, no default region because the upgrade could not create one), the call answers 500 but the account already exists, with no grants and `region_backfill_pending = false`.
  - That account is permanently blind: no later boot repairs it, and a retry gets "Username already exists".
- **Fix:** Make `create` transactional, or move the save and the grant into one `@Transactional` service method (BE-05's `UserAccountService` does this).

### 4. LOW: on Postgres, failing to create the partial index skips the whole region backfill
- **Location:** `B/region/RegionSchemaUpgrade.java:158-164`. The index DDL runs inside `ensureDefaultRegion`. When it throws, `upgrade()` catches the exception at `:81-84` and returns `null`.
- **Detail:**
  - A failed `create unique index if not exists uk_regions_default ...` skips steps 2–7, even though the default region row exists: no customer or child backfill, no NOT NULL, and no legacy grants.
  - Every pre-regions staff user then loses all regional access, and every customer is invisible, until a later boot succeeds.
  - One way to trigger it: two nodes running `CREATE INDEX IF NOT EXISTS` concurrently can fail on Postgres (`pg_class_relname_nsp_index` duplicate key).
- **Fix:** Run the index creation in its own try/catch (WARN and continue), so that only a missing default region stops the upgrade.

## Checked and found correct
These were checked and are not findings:
- **§4.2 formula** in `RegionRights`: SCOPE_OVERRIDE needs ALL, a customer is limited to its own region, `none()` holds nothing, a null region is false.
- **Principal:**
  - `@Transactional(readOnly = true)` principal building.
  - One grants read per Bearer request.
  - No SQL spent deciding scope.
  - Union authorities.
  - `/me` and `/login` shape per §6.2, with `[]` for a customer login.
- **`ScopeResolver` tiers and lists:**
  - Tiers follow §5.6.4.
  - A mixed view carries no chip; a pure book view keeps today's chip (R14).
  - Narrowing is by `ViewScope`, and by-id reads ignore `regionIds` (I3).
  - `PageResponse.of(…, Scope)` is used on the five scoped lists.
- **Creates:** they lock the customer first (F1: customer → sequence → invoice) and copy its region. The `@PrePersist` safety nets are in place.
- **`CustomerService.create` region rule:**
  - An explicit, single-managed or narrowed region is chosen.
  - 400 `fieldErrors.regionId` when none can be chosen; 404, 403 or 400 for an unreachable, unmanaged or inactive region.
  - Nothing is written on a refusal.
- **`RegionSchemaUpgrade`:**
  - SQL is portable to H2 and Postgres.
  - Backfill runs in 1000-id windows.
  - A child takes its customer's region; an orphan dispute goes to the default region.
  - NOT NULL is enforced; the legacy grant is given once and the flag cleared.
  - The enum widening calls are registered.
  - The audit row carries origin SCHEMA.
  - The `ddl-auto=update` boot passes under `halt_on_error`.
- **Clock and migration rules:**
  - Every new clock read goes through `Clock` or `AppClock`.
  - `@ColumnDefault("true")` is used with a Java default of false.
  - `defaultRegion()` is never cached.
  - `@OnDelete(CASCADE)` means a user hard delete (`pocReferenceCount` path) is not blocked by grants.
- **Test reset:** the order matches §3.12, including disputes before customers, grants before regions, and admin and cashier reset to exactly DEFAULT/APPROVE/ALL.
- **Deviations** (`/me` early, the `PrivilegeClassificationTest` subset, `GLOBAL` = 10) are justified.
