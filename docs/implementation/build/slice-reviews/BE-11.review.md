## Findings

### 1. [medium] The recorded event point can come before the versions its own transaction wrote
- Where: backend/src/main/java/com/geneinvoice/history/HistoryWriter.java:84, compared with :146 and :251-253.
- The writer persists `HistoryTransactionRow(txId, t)` with the raw bound instant `t`. The versions the same transaction opens start at `after(t, open)` = `max(t, open.validFrom + 1µs)`, which is later than `t` whenever the previous version began at or after `t`. That happens with cross-instance clock skew, a clock that moves backwards, or equal microseconds. §5.7.5 explicitly designs for all three.
- Consequence: D10 has the consumer evaluate at `AsOfPoint.at(instant)`, so it would see an older state rather than the change that raised the event. That breaks the PRD A5/D10 promise that each event is evaluated as of the moment it happened.
- Proof: the probe updated a customer at T and again with the clock 5 ms behind (another instance). It recorded point = T−5ms while the new version starts at T+1µs, so the state at the point was two versions old ("Acme Ltd" instead of "Acme B").
- The code follows §5.7.4's pseudo-code literally, but that contradicts D10 and §5.7.5.
- Fix: persist the row after steps 3–4 with `max(t, every validFrom/validTo the writer set for opened versions and link rows)`. Alternatively, track `maxFrom` in the writer and record that.
