## Findings

### 1. (medium) The G18 test does not prove the fields re-seed from the *live* invoice
- **Test:** `frontend/test/approvals_test.dart`, "a held invoice edit: the fields go back to what the invoice holds now".
- **Implementation:** `frontend/lib/features/invoices/invoice_detail_screen.dart:171-189` (`_heldForApproval`).
- **Why it is weak:**
  - The fake `GET /api/invoices/42` returns the same `live` map before and after the PATCH (notes 'As agreed').
  - The test then asserts that the notes read 'As agreed'. That value is indistinguishable from the stale first load.
  - Only `notes` is edited. The gated fields (due date and payment term, the ones INVOICE_TERMS holds) are never changed or asserted.
- **Mutation, run in the scratchpad copy `build/mut5`:** I replaced the awaited `ref.refresh(...future)` + `_seed(live)` with `ref.invalidate(invoiceDetailProvider(id)); setState(() => _loadedInto = false);`.
  - That version re-seeds from the cached pre-save value (the `when` shows the previous data during the refresh, so `_seed` locks onto it).
  - **The shipped test still passes.**
  - With the second GET answering `notes: 'Changed by Bob'`, the mutant fails (Expected 'Changed by Bob', Actual 'As agreed') and the real code passes.
  - So the implementation is correct, but the required G18 "re-seed with live values" behaviour (§7.6 row for `invoice_detail_screen.dart`, §8.8 "fields re-seeded") has no regression guard.
- **Fix:**
  - Make the post-PATCH GET answer a different value (e.g. `{...live, 'notes': 'Changed by Bob'}` once the PATCH has been sent) and assert that value.
  - Also change the due date or term before saving, and assert that the due-date field shows the live `dueDate` afterwards.

### 2. (low) The held invoice-edit path uses `context` and `ref` without a `mounted` check after the PATCH await
- **Where:** `frontend/lib/features/invoices/invoice_detail_screen.dart:147-150` → `_heldForApproval` `:173-176` calls `ref.invalidate(...)`, `invalidateApprovals(ref)` and `showSentForApproval(context, held)` before its first `mounted` check (`:183`).
- **Scenario:**
  1. The user edits the due date and presses Save.
  2. While the PATCH is in flight they press Back and choose "Discard". `goGuarded` → `_confirmDiscard` allows the leave, and the state is disposed.
  3. The server answers 202.
  4. `showSentForApproval` looks up `ScaffoldMessenger`/`GoRouter` on a defunct element, which asserts in debug.
  5. The `catch` then calls `setState` on a disposed state (`:163`).
- **Effect:** the user never sees that their "discarded" edit is actually waiting for approval.
- **Context:** the pre-existing applied path has the same unguarded pattern (`setState(() => _dirty = false)` at `:159`). Other FE-05 sites do guard (`if (mounted)` / `context.mounted` in the dispute, invoice-list and override code).
- **Fix:** `if (!mounted) return;` at the top of `_heldForApproval` (after the invalidations, which use `ref`, or with a `mounted` guard around them).

No critical or high findings. No region/as-of leak: the slice adds no reads. `regionIds`/`asOf` still flow through the interceptor, and no write is reachable while historical (unchanged gating).
