# FE-02 review (adversarial)

Checks I ran myself: `flutter analyze` found 0 issues and `flutter test` passed 157 of 157 (logs: build/fe02-review-analyze.log and build/fe02-review-test.log). The diff since the FE-01 snapshot touches only `frontend/`. The only test files it touches are the three new ones, so no baseline test file was edited.

I found nothing critical or high. Every §8.8 acceptance item for region_selector_test, as_of_screens_test and dashboard_coverage_test is present and exercised.

## Medium

### M1. The invoice form (`/invoices/new`) stays fully editable and can be saved on a past date
- Where: `frontend/lib/features/invoices/invoice_form_screen.dart:155-200` (`_submit`, which POSTs `/api/invoices`) and `build` at :204. The file never reads `isHistoricalProvider` or `viewAsOfProvider`.
- FE-02 hides the two entry points: the invoices list button (`invoices_screen.dart:55`, `canManage`) and the dashboard quick action (`dashboard_screen.dart:202`). But the form is a full page inside `AppShell`, and the as-of chip is always in the app bar.
- Failure scenario:
  1. A user opens New invoice while live and starts filling it in.
  2. They tap the chip and pick 30 Jun 2026. The banner says "read only".
  3. The form is still editable, and its customer and product searches now return data as of 30 June, because the interceptor adds `asOf`.
  4. Save POSTs `/api/invoices?asOf=2026-06-30`, and the server answers 400 `AS_OF_READ_ONLY`.
- The same happens when the user reaches `/invoices/new` by URL or with Back while viewing a past date.
- This breaks §7.4 ("Every mutating control ANDs `!ref.watch(isHistoricalProvider)`") and D2 ("the UI disables it too").
- Fix: in `InvoiceFormScreen.build`, watch `isHistoricalProvider`. Disable Save and the inputs, or show the read-only notice in place of the form. Add the screen as a row in `as_of_screens_test`'s `_sites`.

### M2. The dashboard's "today" is cached for the whole session, so after UTC midnight the links and filters use yesterday
- Where: `frontend/lib/features/dashboard/dashboard_providers.dart:199-202`:
  ```dart
  final dashboardTodayProvider = Provider<DateTime>((ref) {
    final asOf = ref.watch(viewAsOfProvider);
    return asOf == null ? todayUtc() : DateTime.utc(asOf.year, asOf.month, asOf.day);
  });
  ```
- It is a plain, non-autoDispose `Provider`. Riverpod works out `todayUtc()` once and keeps the result until `viewAsOfProvider` changes. `refreshDashboard` (:290-299) does not invalidate it.
- Before FE-02, `todayUtc()` was called on every build and fetch: in `_Header`, `AgingBars`, both tables and `upcomingPromisesProvider`.
- Failure scenario:
  1. The dashboard is opened on 26 Sep, and the app stays open, or the user comes back to the dashboard, on 27 Sep (UTC).
  2. Pull-to-refresh sends `promisedDate:gte:2026-09-26` for upcoming promises (`dashboard_providers.dart:268-271`).
  3. The ageing band links compute `dueDate:between` from 26 Sep, and the "days" counts and header range are one day behind.
  4. The server's figures, meanwhile, use the real today.
- This is a regression in live mode, not only in as-of mode.
- Fix: make it `Provider.autoDispose`, invalidate it in `refreshDashboard`, or keep the as-of branch in a provider and call `todayUtc()` at the use site when `asOf == null`.

### M3. On a past date the inbox lists today's mail, but opening a message reads it as of the past date
- Where: `frontend/lib/features/email/email_providers.dart:46-51` (`emailDetailProvider` does a plain `dio.get('/api/emails/$id')`, does not watch the scope and does not call `checkAsOf`), used by the inbox reader at `inbox_screen.dart:174`.
- The inbox list is live: `InboxController` is class-level `@AsOfIgnored` (§5.2.3, D9), and FE-02 treats it as regions-only. But `GET /api/emails/{id}` is method-level `@AsOfAware` (`EmailController.java:67-68`). The interceptor adds `asOf` to that request, and there is no opt-out.
- Failure scenario:
  1. The user views 30 Jun 2026. The inbox still shows a message received today (`bulkWhileHistorical` and the live strip make this list usable).
  2. Tapping the message opens `_ReaderDialog`, which GETs `/api/emails/88?asOf=2026-06-30`.
  3. Today this gets 400 `AS_OF_UNSUPPORTED`. From BE-09b/BE-10 on it gets a 404, because `occurred_at > p`. Either way the dialog reads "Could not load this email: …".
  4. An older message opens with its status as of 30 June, which differs from the live status shown in the row.
- There is a second problem: because the provider watches nothing in the scope, a cached reader result is never refetched when the date changes.
- Fix: the reader must read live. Either (a) let the interceptor honour a per-request opt-out (for example `options.extra['viewScope'] == 'regionsOnly'`, keeping `regionIds` and dropping `asOf`) and use it in `emailDetailProvider` when it is called from the inbox, or (b) give the inbox its own detail endpoint that answers live. Add a region_selector/as_of test: open an inbox message while viewing a past date, and assert that no `asOf` is sent.

## Low

### L1. On a past date the documents tab's Edit and Remove buttons depend only on server flags, and the folded `canManageDocumentsProvider` is never used
- Where: `frontend/lib/features/documents/documents_tab.dart:352-364` (`if (document.canEdit)`, `if (document.canDelete)`). The folded `canManageDocumentsProvider` in `document_actions.dart:17` has no reader anywhere in `lib/` (`grep -rn canManageDocumentsProvider frontend/lib` finds only its definition).
- D14 has the server send `false` when historical, but nothing in `backend/.../document/` does that yet (no historical check in `DocumentService.toDto`). Until BE-04b/BE-10 lands, a past-date documents tab offers Edit and Remove, and they fail with 400 `AS_OF_READ_ONLY`.
- The implementer's report says the document permission is "off" on a past date. That holds for upload (`canUploadDocumentsProvider`, which is read at `documents_tab.dart:147`), but not for edit and remove.
- Fix: AND `!ref.watch(isHistoricalProvider)` into the two icon conditions, as §7.4's "every mutating control" requires. Alternatively, drop the dead folding and record in the log that edit and remove rely on the server flag.

## Checked and fine
- **Region selector:** a `PopupMenuButton` of `CheckedPopupMenuItem`s plus "All my regions". It is hidden for customer logins and for 0 or 1 regions, fetches nothing, becomes an icon below 600px, and sits before the bell. It never produces an empty `regionIds`.
- **As-of chip:** staff only. It reads `historyRangeProvider` only on tap, via `listenManual`, so nothing is fetched at build (G13). The picker runs from `historyStartsOn ?? DateTime(2000)` to `latestAsOf`, falling back to yesterday UTC. When history starts in the future it shows a snack, and × goes back to today.
- **Banner:** the exact text, and "Back to today". It stays in the tree at all times; this deviation is reasonable because it avoids re-mounting pages.
- **DataTableScaffold:**
  - Bulk actions are hidden while historical and export stays. `bulkWhileHistorical` is set only on the notifications and inbox lists, whose bulk endpoints are §5.2.4 housekeeping.
  - The live strip shows when `page.asOf == null`.
  - The "Your book only in" strip requires `bookRegionIds` to be non-empty and `lockedFilters` to be empty.
  - FE-01's selection-clearing `ref.listen` is kept.
- **Scope watching:**
  - The detail providers (customer, invoice, payment, promise, dispute, product) watch `viewAsOfProvider` and call `checkAsOf`. Leaving out regions is consistent with I3.
  - The record-tab providers (promises, disputes, documents list and count, emails, audit) watch the full scope and call `checkAsOf`.
  - All 8 dashboard providers go through `_dashboardGet`, which watches the scope and calls `checkAsOf`.
  - The bell, the inbox count, notifications, `myPocScopeProvider` (now autoDispose, G22), `assignablePocsProvider` and `referenceOptionsProvider` watch regions only.
  - The router does not watch the scope (G4).
- **Read-only gating:** covers the customer, invoice, payment, promise, product, dispute, user and role detail screens and lists, the promises and disputes tabs, email send and Retry, POC assignment, and document upload. Detail edit controllers are seeded only from live data, and read-only cells render the historical entity (not the controllers). I checked the customer, invoice and payment screens.
- **Every other mutating HTTP call site** (`grep -rnE "\.(post|patch|put|delete)\("`) is gated, modal (so it cannot be open while the chip is tapped), or allowed housekeeping (Gmail, change-password, inbox and notification read). The exceptions are M1 and L1.
- **Dashboard:**
  - `Coverage.mixed` parses, unknown values fall back to `all`, and `scope` is parsed.
  - The ageing links, upcoming-promises filter, "days" counts and header use the as-of date.
  - "New invoice" is hidden on a past date.
- **Not-found text:** a 404 while historical reads "This X did not exist on …".
- **Tests:** they drive real widgets through `dioWith([viewScopeInterceptor(...)])`, and they assert the `asOf`/`regionIds` sent, the absence of controls, and the header check. They are not trivially passing.
