## Verified correct (no finding)
- **Gate placement and side effects.** Every entry method follows authorise → validate → gate → mutate. No held path touches a tracked entity before the gate:
  - `createOrHold` draws the number after the gate (InvoiceService.java:121-124).
  - `updateOrHold` works out `Due` and the POC before any setter (:193-211).
  - Promise update and override call their setters only after the gate.
  - `recordOrHold` gates after the targets are sorted (PaymentService.java:122-123).
  - The dispute path is parse → measure → gate → apply.
- **Measures follow §5.11.1:** terms use the balance only when the date moves later; promise update is `max(|Δ|, later ? new : 0)`; override is `BROKEN ? 0 : amount − fulfilled`; the dispute measure is computed per action.
- **Appliers.** Each takes the customer first, then its own row. Approve locks the pending row after them. Three-way checks cover INVOICE_TERMS and PROMISE_UPDATE, and PROMISE_UPDATE is re-based. Strict checks cover INVOICE_CANCEL, PROMISE_OVERRIDE and DISPUTE_APPROVE. "Amount grew" is checked through the gate's apply mode.
- **Lock order.** Deny, approve, supersede and the closer all take the customer first, so there is no lock cycle.
- **PendingChangeCloser.** It is MANDATORY, locks the pending rows after the writer's own locks, skips the row being applied, writes `CHANGE_CLOSED` with a null actor, and sends APPROVAL_CLOSED to the maker. It is called from the applied cancel, the applied dispute approval and deny.
- **Legacy wrappers** keep their signatures and roll back on a hold. The reassign paths always measure 0.
- **SC-10.** The column is set by customer create and update and by the user PUT, and cleared by change-password. The checker step compares the approver with it.
- **Mapping and schema.** The 202 responses go through `Outcomes.respond` on all eight endpoints. `CreatePromiseRequest` has the `@JsonCreator` canonical constructor and keeps the 6-argument constructor. The new users column is nullable, so ddl-auto can add it safely.
- **Clock.** Every clock read goes through the injected primary `Clock`.
- **The acceptance tests from §8.6 exist and pass:** GatePaymentPromiseTest, ApproveFailureTest, ApprovalConcurrencyTest, OutstandingChangeTest, DisputeApprovalGateTest and ExemptPathsTest, plus the BE-14 parts of GateInvoiceTest and ApproveFlowTest.

## Findings

### 1. [medium] SC-10 can still be bypassed: the staff member who set the password can clear `credentials_set_by_user_id` by changing it as the customer
- **Location:** AuthController.java:116 `u.setCredentialsSetByUserId(null);`, checked at DisputeService.java:147-150.
- **Cause:** change-password only needs the current password. The staff member who set that password knows it.
- **Scenario:**
  1. Admin A (CHANGE_APPROVE in North) resets Acme's login password to P via PUT /api/customers/{id}. `credentials_set_by` becomes A.
  2. A signs in as acme.login with P and calls /api/auth/change-password with P → P2. The column is cleared.
  3. A opens a dispute proposing `{"action":"cancel"}` on a ₹5,00,000 invoice.
  4. A signs in as themself and approves it as proposed. `checkerStep` is true, so it applies at once, above every threshold, with no second person.
- **Effect:** This is exactly the one-person path SC-10 exists to close. It follows §3.4/§5.11.8 literally, which say to clear the field on change-password, so this is a design-level hole.
- **Fix (for the design owner):** Do not clear the field on change-password. A change of password by whoever is signed in says nothing about who else set it. Alternatively, keep every staff setter for the login, or block anyone who set that login's password in the last N days.

### 2. [medium] A held dispute `replace_items` change keeps unpinned prices, so the approved total can differ from what the approver saw
- **Location:** DisputeService.java:188 stores `change.json()` as sent. Line 363 reads `unitPrice` as optional. InvoiceService.java:345 prices a line with no `unitPrice` from the catalogue at apply time (via `replaceItems`, DisputeService.java:411).
- **Scenario:**
  1. A 500.00 invoice. The proposal is `replace_items` with one line (product X, qty 4, no unitPrice). X costs 100.00, so the proposed total is 400.00 and the measure is 100.00, above a threshold of 50.
  2. The change is held, and the Detail's proposed view shows total 400.00.
  3. Before approval, X's catalogue price rises to 112.50. The new total is 450.00 and the measure is 50.00, so the gate's apply mode ("the amount grew") does not fire.
  4. The strict check compares only the target's current total, paid amount and status, which are unchanged.
  5. The invoice is re-issued at 450.00, not the 400.00 that was approved.
- **Effect:** For INVOICE_CREATE, §5.11.1 pins every line's `unitPrice` for exactly this reason ("so the invoice the approver agrees to is the one that is made"). The dispute path does not.
- **Fix:** When holding, rewrite the stored change JSON with each `replace_items` line's resolved `unitPrice`. `totalFor` already resolves them.

### 3. [low] Customer logins that existed before BE-14 have no `credentials_set_by_user_id`, so SC-10 does not protect them
- **Location:** User.java (new nullable column; no backfill anywhere) and DisputeService.java:147.
- **Cause:** Every customer login is created by staff with a staff-chosen password (CustomerService.create). Every login that already exists reads null until someone resets its password.
- **Effect:** The admin who created such a customer can approve that customer's proposal as proposed and have it applied alone. §3.4 specifies no backfill, so this is a design gap.
- **Fix:** Backfill from the audit rows (`CUSTOMER_CREATED` actor, or the latest `CUSTOMER_UPDATED` that set a password). Or treat null on a login that has never changed its own password as "set by staff, unknown", and hold the checker step then.

### 4. [low] Test gap: three approval paths are never run to success, and two of the claimed checks are untested
- **Location:** No test in T/approval approves a PROMISE_CREATE, a PROMISE_OVERRIDE or an INVOICE_TERMS change successfully:
  - GatePaymentPromiseTest only checks that they are held.
  - ApproveFailureTest's terms case only reaches "amount grew".
- **Effect:**
  - These branches never run to success: `PromiseChangeApplier.apply` PROMISE_CREATE (:84), the whole of `applyOverride`, and InvoiceChangeApplier `applyTerms` past the gate.
  - Two of the LOG's claims have no test: "PROMISE_OVERRIDE strict on statusOverridden/overrideReason" and the INVOICE_TERMS three-way check.
  - A regression in the payload round trip (for example `CreatePromiseRequest` with `assignees` through `PayloadCodec`) or in the strict check would stay green.
- **Fix:** Add three ApproveFlowTest cases:
  - a held promise create approved;
  - a held override approved, and another one FAILED after a `clearOverride`;
  - a held terms change approved, and another one FAILED "Due date was changed by someone else".

### 5. [low, BE-15 hand-off] `everyLimitAtZero` will break once THRESHOLD_CHANGE is appended
- **Location:** ApprovalTestBase.java:164-166 loops over `ApprovalOperation.values()`.
- **Effect:** §3.8 says `approval_thresholds.operation` is "never THRESHOLD_CHANGE", and BE-15 appends that constant. The helper will then insert a THRESHOLD_CHANGE threshold row. That is harmless at best; at worst it trips the validation or tests BE-15 adds.
- **Fix:** Loop over `values()` filtered by `amountGated()`.

## Not findings (checked; acceptable or documented)
- **Rethrowing TX-A's own failure** (the ApprovalService.inTransaction deviation) only changes which exception escapes when the rollback itself fails. Nothing was committed, and 409 mapping is kept. The case is specific to H2 and Hikari. On Postgres there is no lock_timeout, so an approval blocked on the customer waits instead of returning 409; that is outside this slice.
- **The 3-second lock test** (ApproveFailureTest.java:212-251) depends on H2's default lock timeout being shorter than the 3 s hold. Its margin is thin under heavy load. It passed in the reviewer's run and in the implementer's three extra runs.
- **`closeForRecord` also matches `affected_*`.** Cancelling an invoice therefore closes a waiting DISPUTE_APPROVE on it, and the dispute itself stays PENDING. This is documented, and such a change could only fail anyway. `cancelWithRefund` (the dispute internals) does not call the closer, and §5.11.7 does not ask it to. A pending INVOICE change on a record a dispute cancelled fails on approval with the rule's message.
- **Pending changes on one sum of money.** A DISPUTE_APPROVE (`DISPUTE:x`) and an INVOICE_CANCEL (`INVOICE:y`) on the same money can both be pending, because the outstanding keys are per entity (§5.11.7). Whichever is approved second fails.
- **Deferred to BE-19 as documented:** CUSTOMER-target and `none` dispute rules, check 5a, `internal_source`, and applying promise co-assignees.
- **Still open from the BE-13 review:** money sent as doubles, `Location` missing from the CORS exposed headers, check 4 untested, and strict fields missing from `changes[]`.
