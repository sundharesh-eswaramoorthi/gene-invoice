## Findings (most severe first)

### 1. [medium] RunViews shows the true `matched` count to viewers who only get partial counters, and the test pins that behaviour
- **Where:** `B/automation/run/RunViews.java:168` passes `run.getMatched()` unchanged. `viewersCounters` (:186-202) recounts only done, skipped and failed. `T/automation/run/RunViewsTest.java:98` asserts `matched == 3` for Vic, who can see only SOUTH.
- **What goes wrong:** §5.10.10 and §6.14 say `RunDto` counters, *including `matched`*, are recomputed over the effects whose target the viewer can see, with `partial: true`. Today a SOUTH-only viewer of a set run (manual, schedule or CHILDREN) learns how many NORTH records matched. That is a B1 "figure scoped by which regions" leak.
- **Fix:** for a non-full viewer, set `matched` to the number of distinct visible targets among the run's effects (or null it when `partial`), and change RunViewsTest:98 to expect 2.

### 2. [medium] `drain` loops for as long as anything is due, but reuses the start-of-drain `now` for every lease and never recovers expired leases again
- **Where:** `B/automation/run/AutomationWorker.java:81-95` (`while (!stopping)`, which re-queries `findDueIds`) and :86 (`leaseUntil = now.plusSeconds(lease)`, where `now` is the drain parameter). Lease recovery (:77-79) runs only once, at the start.
- **What goes wrong:** new events have `next_attempt_at = null`, so they are always due. Under steady save traffic one drain call never returns (§5.10.6 step 3 reads one batch per drain). Every event claimed more than `lease-seconds` (300) after the drain began gets a lease that has already expired. Another node's drain then recovers it and processes it at the same time. The unique keys stop duplicate tasks, but the second pass writes extra SKIPPED "Already done" effects, which inflate the recounted `skipped`. Meanwhile, on this node, events stuck in PROCESSING from a crashed worker are never recovered while the loop keeps finding work.
- **Fix:** take a fresh `clock.instant()` for each claim's lease (and for the `claim` update's `now`), and bound the loop (for example, a few batches or a time budget) so the next poll runs recovery again.

### 3. [medium] Requeue and retry reset the fencing token (`claims = 0`), so an old stale worker's token becomes valid again
- **Where:** `B/automation/event/AutomationEventRepository.java:104-111` (`requeue` sets `e.claims = 0`), used by `RuleService.requeueEvent` (`RuleService.java:562-564`) for both `POST /events/{id}/requeue` and `POST /runs/{id}/retry`.
- **What goes wrong:** the "DEAD after 20 claims" case exists exactly because workers keep losing their leases, so hung workers holding tokens 1..20 may still be alive. After a requeue, the next claim gets token 1 again. A hung worker holding token 1 that wakes up passes the fence (`status='PROCESSING' and claims=:token`) in `finishDone`, `finishRetry` or `heartbeat`. It can mark the event DONE while the new worker is still mid-run, or overwrite its outcome. That breaks the §5.10.6 and §8.5 promise that "a stale worker cannot overwrite the outcome".
- **Fix:** keep `claims` monotonic. Add a `claims_base` column, or store the claims value at requeue and compare `claims - base > max-claims`, rather than resetting the token.

### 4. [low] Per-rule CHILDREN events ignore `active_since`, so a resumed or re-enabled rule can act on backlog
- **Where:** `B/automation/run/RuleRunner.java:141-149` and :225-228. `active(rule, manual)` checks deleted, suspended and enabled only. `active_since` is applied only when the fan-out picks its candidates (`EventProcessor.fanOut` → `findEntityCandidates`).
- **What goes wrong:** a per-rule CHILDREN event fanned out at T0 can still be PENDING (for example, in retry backoff of up to 1 h). If the rule is then disabled and re-enabled, or suspended and resumed with `replay=false` (`active_since = now`), the event still acts. That contradicts §3.6 ("entity events with occurred_at < active_since are ignored") and §5.10.7 ("replay = false: the backlog is not acted on").
- **Fix:** for CHILDREN events, re-read `activeSince` in `runForSet` and skip when `ev.occurredAt < activeSince`.

### 5. [low] Run progress and run finish are not fenced by the token
- **Where:** `RuleRunner.java:192-196` runs `setProgress` and `heartbeat` in one transaction and commits `setProgress` even when `heartbeat` changes 0 rows. The `settle`/`finish` calls (:276-320) never check the token either. The pre-loop reset (:157-168) sets `matched = 0` and `truncated = false` unconditionally.
- **What goes wrong:** a worker that lost its lease still overwrites the run's `matched`/`truncated` counters (which are not recounted from effects), and can finish the run while the new owner of the event is still working. §9.1 gotcha: "Fencing on every finish."
- **Fix:** do the heartbeat first and roll back (`s.setRollbackOnly()`) when it changes 0 rows. Fence `settle` on the event's token as well, for example with a `claims = :token` check in the same transaction.

### 6. [low] The runs list filters on unredacted columns, so a partial viewer can find out things the rows hide
- **Where:** `RunController.java:55-56` passes the request's filters and sort to `RunViews.runs` (`RunViews.java:99`). The `AUTOMATION_RUNS` schema (`TableSchemas.java:542-558`) makes `entityId`, `matched`, `done` and `failed` filterable and sortable against the stored values.
- **What goes wrong:** a SOUTH-only viewer can ask `GET /rules/{id}/runs?filter=entityId:eq:<north invoice id>`. `totalElements` then shows whether the rule acted on a record they cannot see, even though each row hides `entity`. `failed:gt:0` filters on the unredacted counters in the same way.
- **Fix:** for non-full viewers, refuse (400) or drop filters and sorts on `entityId`, `matched`, `done`, `skipped` and `failed`.

### 7. [low] One part of an acceptance test is deferred
- **Where:** `RunNowTest` has no assertion for "after running the rule's CREATE_DISPUTE they cannot approve the resulting change (400)" (§8.5, SC-2).
- **Status:** logged as a gap because CREATE_DISPUTE `perform` arrives in BE-19. BE-19 must add this assertion to RunNowTest (or to DisputeActionTest).
