## Findings (most severe first)

No critical, high or medium defects were found. Four low findings follow.

### 1. LOW: inbox "mark all read" ignores `regionIds`, so it marks emails the narrowed view never showed
- **Location:** `B/email/InboxController.java:84-85` calls `service.markAllRead(userId)`, and `B/email/InboxService.java:51-52` does the same. Neither takes the asked regions. By contrast, the list (`:54-58`), the unread count (`:64`) and bulk (`resolveIds`) all apply `EmailRegionPredicate`.
- **Scenario:**
  1. A user narrowed to SOUTH sees the SOUTH emails and a SOUTH unread badge.
  2. They click "Mark all read".
  3. Every NORTH email is marked read as well, although it was never shown.
  4. When they widen the view again, the NORTH emails look already read.
- **Status:** The implementer disclosed this as a gap. §5.2.4 lists the endpoint as housekeeping, and §6.7 says only "bulk" POSTs honour `regionIds`. So this conflicts with B1 ("every list/filter/count") rather than with a line of the spec.
- **Fix:** When `askedRegions()` is non-null, mark only the rows matching `EmailRegionPredicate`. Alternatively, have the UI send `/bulk` with `selectAllMatchingFilter`. Do the same for notifications in BE-04b.

### 2. LOW: emails about a deleted record drop out of a narrowed inbox and its unread count
- **Location:** `B/email/EmailRegionPredicate.java:49-52`.
  - Only a USER, ROLE or PRODUCT type, or an `entityId IN (select id from X where region.id in :regions)`, is kept.
  - After `CustomerService.delete` (`deleteById`, with `EmailCascade.onCustomerDeleted` setting `entityDeleted = true`), the id is in no table.
  - So every email about that customer disappears whenever `regionIds` is set, in every region. It is still listed without `regionIds`.
- **Status:** The implementer disclosed this gap. The spec's predicate (§5.6.7) is followed literally, but the answer to "which regions" then depends on whether the record still exists.
- **Fix:** Also keep rows with `entityDeleted = true`. Or, to stay region-exact, resolve their region from `audit_logs.region_id` (the `findLatestRegionId` that BE-04b adds).

### 3. LOW (test): `RegionBookTest` never narrows to a granted region where the user's tier is NONE
- **Location:** `T/region/RegionBookTest.java:155-172`.
  - `sam` holds DEFAULT (bridge) and SOUTH only.
  - The loop narrows to WEST and to NORTH, and both are ungranted.
- **Problem:** The LOG describes the second case as "a region where the user holds nothing". It is the same case as the first. The §5.6.4 step-3 branch is not exercised: a region that is granted but has tier NONE, while another granted region is visible, should give no chip. A regression that put the chip back in that case would pass.
- **Fix:** Give sam a grant in NORTH that yields tier NONE for invoices (for example a READ/ALL grant, if `POC_ASSIGNABLE_SALES` needs MANAGE). Then assert `regionIds=N` → `totalElements == 0`, `lockedFilters == []` and `regionIds == []`.

### 4. LOW: `topPaying` now breaks ties by Java string order instead of the database's `ORDER BY name`
- **Location:** `B/dashboard/DashboardService.java:197-205`.
  - Each part's SQL still orders by `desc(total), asc(name)`.
  - The merged list is then re-sorted with `Comparator.naturalOrder()` on `customerName`.
- **Scenario:** On Postgres with a linguistic collation, two customers with equal "collected" whose names differ in case or accents come back in a different order than before, even for a single-region user with one part. F2 says the single-region answer is identical to today's.
- **Fix:** Skip the re-sort when there is only one part. When merging, keep the SQL order within each part and merge by amount only, keeping the first part's order on ties.

## Checked and found correct
- **§6.5 DTO fields.**
  - `regionId`, `regionCode` and `regionName` are on `CustomerDto`, `InvoiceDto`, `InvoiceSummary`, `PaymentDto`, `PromiseDto` and `DisputeDto`.
  - Each field has component-level `@JsonInclude(NON_NULL)`. The deviation is justified: a class-level annotation would drop today's null `salesPoc` and `pocMissing` (P7).
  - `"region"` was added to every list and `allMatching` fetch list, so there are no per-row region loads.
  - A LAZY region is only read on paths with OEMIV or inside a transaction. `/api/emails` and `/api/inbox`, which run without OEMIV, build none of these DTOs.
- **`TableSchemas` / `TableSchemaController`.**
  - The five schemas have `regionId` (REFERENCE, `region`) and `regionName` (TEXT, sortable).
  - `TableSchemaController` uses `Map.ofEntries` with `List` values and any-of `mayRead`.
  - CSV exports use hand-written columns, so they are unaffected.
- **Dashboard (§5.12).**
  - Part A uses the payment scope's FULL regions with the payment predicates, `region ∈ A` and ACTIVE.
  - Part B requires `invoice.region ∈ (pay.book ∪ inv.book)` and (invoice ∈ `idsInScope(inv)` or payment ∈ `idsInScope(pay)`), with the outer `cq` passed.
  - A ∩ B = ∅ holds: FULL for either kind needs SCOPE_OVERRIDE in the region, and I1 keeps each payment in its invoice's region.
  - Months are added part by part. `topPaying` limits each part, then merges and limits again.
  - The collected coverage and `ScopeInfo(A ∪ B, B, asOf)` match the spec. So do the other figures (OWN, then BOOK for the chip, then MIXED, then ALL, with `scopeInfo`).
  - A customer login keeps today's payment path.
- **Single-region F2.** Worked by hand for admin, a PAYMENT_VIEW+SCOPE_OVERRIDE role, SALES_POC and collection-only roles, the pre-change formula and the new one agree. `RegionBookTest` asserts this.
- **Email bulk.** `EmailTargets.bulkIds` uses `scope(kind, VIEW, SELECTED, EMAIL_SEND)`. The test is valid: CASHIER holds SCOPE_OVERRIDE, so without EMAIL_SEND the READ-only NORTH region would be offered, and the test would catch that.
- **Inbox.**
  - The predicate applies only when `regionIds` is set, and regions are narrowed to the granted ones.
  - USER, ROLE and PRODUCT emails are always kept. `entity_type` is NOT NULL, so the `NOT IN` is safe.
  - An empty asked set never produces `in ()`.
  - The list, unread count and bulk share one predicate. A customer login is not narrowed. `lockedFilters` stays `[]` (R14).
- **Inventory.** Every current endpoint is in exactly one region list. The inbox and notifications are in SETS and classified IGNORED. The coverage-test rows ∪ `PENDING_ROWS` equal SETS. All three acceptance tests exist and pass.
- **No new code risks.** There are no new clock reads, no new user-referencing tables, no background use of `currentUser.require()`, and no DDL changes.
