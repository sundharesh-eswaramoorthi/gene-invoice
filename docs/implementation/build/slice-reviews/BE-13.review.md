## Verified correct (no finding)
- The gate is placed after lockForWrite (customer lock, then invoice lock, visibility, requireLive, requireIn INVOICE_MANAGE) and after the cancel's business checks, and before any mutation (InvoiceService.java:405-420). On the held path nothing is saved, audited as INVOICE_CANCELLED or published. The test compares outbox and version counts, so it would catch a leak.
- Approve binds the APPROVAL origin (actor = maker) around TX-A (ApprovalService.java:111-112). TX-B re-reads under lock and checks `isPending` (:115-125). Checks run in the order 1-4, then 5 (400), then 6 (403). Refusals of the re-run become FAILED. Concurrency and integrity errors propagate as 409. The unlocked peek is detached before the locked read. `open-in-view: false`, so TX-A and TX-B do not share a persistence context.
- Lock order is consistent. Approve takes customer, then invoice, then pending. A maker's supersede takes customer, then invoice, then UPDATE pending. Reject and withdraw lock only the pending row. There is no lock cycle.
- Supersede and conflict follow §5.11.7. Bulk reports `pending` and skips on 409. `BulkResult.pending` is always present.
- The reset order, `pocReferenceCount`, the privilege classification, and the rule that granting APPROVE needs CHANGE_APPROVE (on both replace and create) are all correct. APPROVER_ADDED goes to the region's other holders.
- Clock reads go through the injected (primary) Clock bean. Enum columns use converters (varchar, no CHECK). The TEXT columns follow the existing `@Lob TEXT` convention.

## Findings

### 1. [low] Detail `current`, `proposed` and `changes[]` send money as doubles (500.0), not 2-decimal numbers
- **Location:** PayloadCodec.java:56-63 (`tree` uses `mapper.readTree`), used by PendingChangeViews.java:94-98.
- **Cause:** The Boot ObjectMapper does not enable USE_BIG_DECIMAL_FOR_FLOATS (nothing in application.yml or the code sets it). `readTree("{\"total\":500.00}")` therefore produces a DoubleNode, which serialises as `500.0`.
- **Effect:** §6.0 says money is "a JSON number with 2 decimals". GateInvoiceTest only compares with `decimalValue()`, so it cannot see the difference.
- **Fix:** Build the tree with `mapper.reader().with(DeserializationFeature.USE_BIG_DECIMAL_FOR_FLOATS)`, or enable that feature on the codec's private mapper copy.

### 2. [low] The Detail never flags a strict-check field that changed since the request
- **Location:** PendingChangeViews.changes (PendingChangeViews.java:161-172).
- **Cause:** A field whose base equals its proposal is skipped (`if (was != null && was.equals(becomes)) continue;`). For INVOICE_CANCEL, `total` and `paidAmount` are the strict-check fields, and they are never listed.
- **Scenario:** Cancel held with total 500. The invoice is later edited to 700. The approver's Detail shows one row, `status`, with `changedSinceRequest:false`. Approving then FAILs with "Total was changed by someone else" (InvoiceChangeApplier.java:71-73). Only the raw `current` object shows the drift.
- **Fix:** For strict operations, also emit rows (or set a flag) for base fields where `current != base`.

### 3. [low] The 202 `Location` header is not readable by a cross-origin browser client
- **Location:** SecurityConfig.java:49 `cfg.setExposedHeaders(List.of("Authorization", ViewScopeInterceptor.HEADER))`.
- **Cause:** Outcomes.respond sets `Location: /api/approvals/{id}` (Outcomes.java:25-27). `Location` is not a CORS-safelisted response header.
- **Effect:** FE-05 `pendingFrom` and FE-04's thresholds screen fall back to `Location` when the body has no id. On Flutter web served from another origin, that fallback always sees null. The body normally carries `pendingChange.id`, so this affects only the fallback. SecurityConfig is not in BE-13's file list, so this is cross-stream.
- **Fix:** Add `HttpHeaders.LOCATION` to the exposed headers.

### 4. [low, BE-15 hand-off] Threshold rows will make regions undeletable
- **Location:** ApprovalThreshold.java:30-32 (FK to `regions`) and RegionService.delete (RegionService.java:157-172).
- **Cause:** `approval_thresholds.region_id` is an FK to `regions`. RegionService.delete refuses only for customers, disputes or grants, then deletes and flushes.
- **Effect:** A region with any threshold row gets a 409 integrity error on delete. §5.11.11 has every new region copy the default region's thresholds (BE-15 `onRegionCreated`). Once that lands, every region created while the default has thresholds can never be deleted. Nothing creates thresholds through the API in BE-13, so this is latent today. RegionService.delete is not in BE-15's Modify list.
- **Fix:** BE-15 should delete the region's threshold rows in RegionService.delete, or list them in the refusal message.

### 5. [low] Test weakness: "customer login → 403" never reaches the service's check 4
- **Location:** ApproveFlowTest.java:131-133.
- **Cause:** The customer role lacks CHANGE_APPROVE, so `@PreAuthorize(CHANGE_APPROVE)` (ApprovalController.java:36) rejects the request before `ApprovalService.requireDecidable`'s `caller.getCustomerId() != null` check (ApprovalService.java:218).
- **Effect:** Deleting check 4 would not fail any test. Check 4 matters from BE-14, when customer logins become makers of dispute proposals. A customer role granted CHANGE_APPROVE by an admin would then rely on it alone.
- **Fix:** Add a service-level test that grants a customer role CHANGE_APPROVE and asserts 403.
