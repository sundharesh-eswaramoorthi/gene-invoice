## 1. [medium] A region with approval limits can no longer be deleted, and every new region now starts with limits
- Where: `approval/ApprovalThresholdService.java:707-722` (`regionCreated` copies the default region's rows), `region/RegionService.java:173-190` (`delete`), `approval/ApprovalThreshold.java:31` (`region_id` is a real FK to `regions`).
- Detail: `RegionService.delete` refuses a region only when it has customers, disputes or grants. Otherwise it deletes the grants and then the region, and flushes. It never removes the region's `approval_thresholds` rows. Since BE-15, a new region receives a copy of every DEFAULT threshold. So once DEFAULT has any limit, deleting a region created by mistake hits the FK at the flush, and the method's own comment says that answers 409. The limits cannot be cleared first either: a PUT with `amount: null` is a loosening, so it is held as a THRESHOLD_CHANGE. That needs a second `CHANGE_APPROVE` holder in a region whose only approver is usually its creator (the thresholds view even warns "Nobody else can approve"). Any THRESHOLD_CHANGE row (pending, approved or rejected, since `pending_changes` is never purged) also references the region, so once a loosening has been requested there, the region can never be deleted. Before BE-15 an empty region could always be deleted, because nothing created thresholds outside tests.
- Fix: in `RegionService.delete`, delete the region's `approval_thresholds` rows along with its grants. Also decide what to do about THRESHOLD_CHANGE rows: refuse with a 400 while one is PENDING, and allow the delete, or deactivate instead, once they are decided. Add a RegionAdminTest case: DEFAULT has a limit, create a region, delete it → 200.

## 2. [low] A customer login's audit trail hides the applied change itself, not just the request, when the change came from an internal dispute
- Where: `audit/AuditTimelineService.java:1863-1866` (in the timeline loop):
  `if (customerView && (TASK.equals(e.entityType()) || (pc != null && pc.isInternalSource()))) continue;`
- Detail: §5.13 and §5.11.11 say that for a customer login, "`CHANGE_*` rows whose pending change has `internal_source = true` are dropped". The code drops every entry that carries such a `pendingChangeId`. That includes the rows written when an approved change is applied, such as `INVOICE_CANCELLED` or `PAYMENT_VOIDED` on the customer's own invoice. Those rows carry `pending_change_id` through `WriteOrigin.approval`. The customer then sees their invoice cancelled with no history entry for it. It is latent until BE-19 sets `internal_source`, and the ApprovalVisibilityTest SC-1 case only asserts that `CHANGE_*` rows are absent.
- Fix: apply the `internal_source` filter only when `e.action().startsWith("CHANGE_")`. Optionally null `pendingChangeId` and `pendingStatus` on the kept applied row.

## 3. [low] A customer login reads the checker's decision note through the audit trail, although the approvals API hides it
- Where: `approval/ApprovalService.java:269-270` (`CHANGE_APPROVED`, reason = note) and `:292-293` (`CHANGE_REJECTED`, reason = note); `audit/AuditTimelineService.withoutPocIdentity` (lines 1896-1913 of the diff) keeps `reason`.
- Detail: §6.11 and §5.11.9 null `decisionNote` for customer logins on for-record and on the Detail, and PendingChangeViews does this. But `CHANGE_REJECTED` and `CHANGE_APPROVED` rows on INVOICE, PAYMENT and PROMISE stay in the customer's trail, because only CUSTOMER-level `CHANGE_*` rows are dropped, and their `reason` is the checker's note. `ApprovalAuditTimelineTest.aHeldCreatesRowsAreOnTheCustomer` shows a reject note stored as `reason` ("Wrong customer"). So `GET /api/audit?entityType=INVOICE&entityId=…` as the customer shows the internal note that the approvals API redacts.
- Fix: in `withoutPocIdentity`, null `reason` on `CHANGE_APPROVED`, `CHANGE_REJECTED`, `CHANGE_WITHDRAWN` and `CHANGE_CLOSED` rows (or on every `CHANGE_*` row except `CHANGE_REQUESTED`).

## 4. [low] As of a date, the approvals list's `status` filter uses today's status
- Where: `common/query/TableSchemas.java` APPROVALS `status` column (plain attribute path, lines 2027-2028 of the diff); `approval/PendingChangeScope.forList` adds only the interval.
- Detail: as of D5, a change that was PENDING then but is SUPERSEDED now is returned with `statusAt: PENDING`. The filter `status:eq:PENDING` still drops it, and `status:eq:SUPERSEDED` returns it for a day on which it was waiting. B3 asks that lists answer as of the date. The implementer logged this as a known gap. It is listed here so that it is decided rather than forgotten: map `status` to the at-T value, or refuse a `status` filter in historical mode.

## Checked and found fine (no finding)
- Lock order: approve THRESHOLD_CHANGE takes region, then threshold rows, then pending (`ThresholdChangeApplier.lockDomainRows`), and so does PUT (`lock()`, then `hold`). The move takes customer, then invoices, then pending (the participant's `findForCustomerForUpdate`). Customer delete takes customer, then pending.
- Cumulative window: the usage query runs only when a row exists, the change alone is within it, window > 0, and there is a maker and a customer. Approved changes are not counted, because apply mode returns before the window. A held change's `amount` stays its own measure.

- `pendingApproval` EXISTS works on version roots (`VersionRow.id` = `entity_id`). Customer logins exclude `internal_source` in both the filter and the DTO flag.
- The 409 for another maker's THRESHOLD_CHANGE rolls back the tightening already flushed (a runtime exception inside `@Transactional`).
