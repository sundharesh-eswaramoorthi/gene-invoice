## MEDIUM

### M1. Region PUT / DELETE can overwrite a concurrent make-default: zero (or, on H2, two) default regions
- `Region.java:37-38`: `is_default` is an ordinary updatable column; `Region` has no `@DynamicUpdate`, so every ORM UPDATE writes it back.
- `RegionRepository.clearDefaultExcept` / `markDefault` are bulk JPQL updates that do **not** bump `version` (a deliberate deviation, "so a version the client already holds stays valid").
- `RegionService.update` (`RegionService.java:643-666`) loads the region, then `saveAndFlush` writes the full row, `is_default` included, with `where id=? and version=?`. `RegionService.delete` (`:694-712`) checks `isDefaultRegion()` on its load, then deletes `where id=? and version=?`.
- Failure scenarios (Postgres READ COMMITTED; H2 is the same or worse):
  1. T1 `PUT /api/regions/A {"name":"A2","version":0}` loads A (is_default=false). T2 `POST /api/regions/A/make-default` clears DEFAULT, marks A, commits. T1's UPDATE waits on T2's row lock. It then finds version still 0 and writes `is_default=false`, so **no region is the default**. `RegionService.defaultRegion()` then throws `IllegalStateException` (500) for `AuditController.deletedCustomerReachable` and `DataSeeder`. Nothing repairs it until a restart runs `RegionSchemaUpgrade`, and only if the DEFAULT code still exists.
  2. T1 `DELETE /api/regions/A` passes the "is the default" check, then T2 makes A the default and commits. T1's `delete where id=? and version=0` still matches, so the new default is deleted and no default remains.
  3. T1 `PUT` on the current default D (loaded is_default=true) while T2 makes B the default. T1 writes `is_default=true` back on D. Postgres rejects this through `uk_regions_default` (409). **H2 has no such index, so two defaults result**, and `findByIsDefaultTrue` then throws `IncorrectResultSizeDataAccessException` (500).
- The deviation note "The region PUT doesn't touch the default flag" is wrong at the SQL level. The design's invariant (§3.2: exactly one default, kept on H2 by `RegionService`) is broken under concurrency.
- Fix: serialise region writes on a row lock. Add `RegionRepository.findByIdForUpdate` (`@Lock(PESSIMISTIC_WRITE)`) and use it in `update`, `delete` and `makeDefault`. `makeDefault` should also lock the current default, in ascending id order. Alternatively, map `defaultRegion` with `@Column(updatable = false)` so the ORM never writes it (this covers the PUT case), and lock in `delete`/`makeDefault`. Locking in `makeDefault` also closes the acknowledged H2 double-make-default gap.

## LOW

### L1. `PUT /api/regions/{id}` without `version` silently skips the stale check
- `RegionService.java:648`: `if (in.version() != null && !in.version().equals(region.getVersion()))`. `UpdateRegionRequest.version` has no `@NotNull` (`RegionDtos.java` UpdateRegionRequest).
- §6.3 specifies the body as `{"name","active","version"}` with "409 stale version". A client that omits `version` gets last-write-wins. The slice's own tests rely on this: `RegionAdminTest.java:209,213,253` PUT without a version.
- Fix: `@NotNull Long version` (and update those tests), or document the deviation.

### L2. Deleting a region makes the history of customers once deleted from it unreadable to everyone
- `AuditController.java:153-157` `deletedCustomerReachable` takes the region from the `CUSTOMER_DELETED` audit row (`findLatestRegionId`) and requires `currentUser.rights().holdsAnyIn(regionId)`.
- `RegionService.delete` (`:702-704`) blocks only on current customers, disputes and other users' grants. A region whose customers were all deleted can therefore be deleted too, and its grants are deleted with it.
- Scenario: customer C in region X is deleted, then X is deleted. `GET /api/audit?entityType=CUSTOMER&entityId=C` now returns 404 for every caller, admin included, because nobody can hold a grant in a region that no longer exists. The design wants a deleted record's history kept readable to those who could reach its region.
- Fix: in `deletedCustomerReachable`, fall back to the default region (as for a pre-regions customer) when the recorded region no longer exists, or refuse the region delete while audit rows reference it.

### L3. Any-of gates tested only with principals holding the USER_MANAGE side
- §8 RegionAdminTest: "`/api/table-schemas/regions` needs REGION_VIEW or USER_MANAGE". `regionsAreReadBy…` (`RegionAdminTest.java:291-319`) tests a USER_MANAGE-only role and admin, who holds both, plus a cashier holding neither. No principal holds REGION_VIEW without USER_MANAGE.
- So the REGION_VIEW branch of `RegionController.READ` (`RegionController.java:157-158`) and of `TableSchemaController` `regions -> [REGION_VIEW, USER_MANAGE]` is never exercised. Dropping REGION_VIEW from either list would stay green.
- Fix: add a `REGION_READER` role holding REGION_VIEW only, and assert 200 on `/api/regions`, `/api/regions/{id}` and `/api/table-schemas/regions`, and 403 on `/api/regions/{id}/grants`.
