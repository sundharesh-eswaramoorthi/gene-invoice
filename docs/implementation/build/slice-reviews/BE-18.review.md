## Findings (most severe first)

### 1. [medium] A replay that suspends the rule part way reports success and silently drops the rest of the window
- **Where:** `automation/run/RuleRunner.java:134-137` (hourly limit in `runForRecord`), `:156` (owner unavailable), `:379-380`, `:385`, `:397` (the `replay` loop).
- **What happens:** When a replayed change trips the hourly limit, `runForRecord` suspends the rule (RATE_LIMITED) and returns DONE. An OwnerUnavailable or definition failure does the same (suspend, then DONE). The replay loop then:
  - counts the change as replayed (`p.matched++`), moves the cursor past it, and carries on;
  - for every later change in the page, hits the same check, which returns DONE, so each is also counted and passed.
- **How the run ends:**
  - On a short page (any window under `page-size` = 500 changes, so the usual case) there is no `stillRunning` check. `settle` finishes the REPLAY run SUCCEEDED with "Replayed N changes made while the rule was suspended", although most of them were never evaluated.
  - On a full page it ends PARTIAL "Stopped: rule is not active".
- **Why the dropped changes are lost for good:** A later `resume(replay=true)` replays `[newSuspendedAt, now)` only, so the dropped changes, which are older than the new suspension, can never be replayed.
- **Likely in practice:** A replay after a long suspension is exactly when 1000 actions an hour is most likely to be exceeded.
- **Fix:** Re-read the rule (or check the limit) before each replayed change. When the rule stopped, checkpoint at the last change actually handled and finish PARTIAL with the RATE_LIMITED or owner message. Never settle SUCCEEDED after the rule was suspended mid-replay. Also add a ResumeReplayTest case with `maxActionsPerRulePerHour` below the window size.

### 2. [low] Events that happened before the suspension but were processed during it are neither replayed nor counted
- **Where:** `RuleService.resume` (window `[suspendedAt, now)`, `RuleService.java` near `:419-450`); `AutomationEventRepository.findReplayable` (`occurredAt >= :from`); `EventProcessor` candidates skip suspended rules when the event is processed.
- **What happens:** An event with `occurred_at` before `suspended_at` that was still PENDING when the rule was suspended goes like this:
  - It is processed while the rule is suspended, so the rule is not a candidate and the event goes DONE with no run.
  - It is outside the replay window, and outside `skippedWhileSuspended`.
- **When it happens:** consumer backlog or outage, or a proactive OWNER_INACTIVE suspension while events queue.
- **Race variant:** An event that is PROCESSING while the resume commits (it read its candidates while the rule was suspended) and goes DONE after the REPLAY cursor has passed it is also missed.
- **Spec status:** This follows §5.10.7's literal window, but conflicts with A5 "nothing lost when the consumer is down".
- **Fix:** Start the window at the earliest event not yet processed when the rule was suspended, or record `suspended_at` as the rule's `last processed occurred_at`. Otherwise record it as a known limitation.

### 3. [low] Long set runs spend a retry attempt on every page that hits a transient failure, and progress never gives attempts back
- **Where:** `RuleRunner.java:236` (`if (p.transients > 0) return retry(...)` per page); `AutomationEventRepository.yieldAt`/`checkpoint` (neither resets `attempts`).
- **What happens:** Each page with any TRANSIENT action (a lock timeout against a user's save, for example) sends the whole event to RETRY:
  - `attempts+1`, with backoff of 30 s, 2 m, 10 m, then 1 h;
  - a checkpoint or yield after real progress does not reset `attempts`.
- **Result:** A run of many pages that meets 5 sporadic lock conflicts in total goes DEAD ("Gave up after 5 attempts"), its run FAILED and the rest of the slot unprocessed. It also stalls for up to an hour in between. In BE-17 the run continued through all pages and retried once at the end.
- **Mitigation:** The impact is bounded by `maxRecordsPerRun`, which defaults to 1000 (2 pages).
- **Fix:** Reset `attempts` on a successful checkpoint or yield, or continue through the pages and retry only at the end.

### 4. [low] `{{Rule.Name}}` is accepted in hand-written emails and always renders blank
- **Where:**
  - `PlaceholderCatalogue.offered(EmailEntityType)` (`PlaceholderCatalogue.java:~104`) returns `offered(TriggerEntity)`, which includes `COMMON` = Today and Rule.Name, for CUSTOMER, INVOICE and PAYMENT.
  - `RecordContexts.renderForEmail` (`RecordContexts.java:134`) only puts `Today`.
- **What happens:** A manual invoice email with `{{Rule.Name}}` passes validation and is saved with "" plus a warning, instead of the 400 "is not available on invoice emails". §5.10.4 lists no rule level for manual emails.
- **Fix:** Offer `Customer.*` + record + `Today` only for manual emails, as already done for PROMISE and DISPUTE.

### 5. [low] The purge scans two ever-growing tables every 30 s without an index to use
- **Where:** `ScheduleTicker.purge` (every tick).
  - `AutomationEventRepository.findPurgeableIds` filters `status='DONE' and processedAt < :before order by id`. There is no index on `processed_at`, and `idx_automation_event_due (status,next_attempt_at)` does not help with DONE, which is most rows.
  - `HistoryTransactionRowRepository.findIdsBefore` filters `instant < :before order by id`, and `history_transactions` has only `idx_history_tx(tx_id)`.
- **Result:** Both tables get a row for almost every write. When nothing is old enough, each tick scans the whole table.
- **Fix:** Purge once an hour or once a day rather than every tick, or add indexes on `(status, processed_at)` and `(instant)`. Both are additive, so they are safe under ddl-auto.
