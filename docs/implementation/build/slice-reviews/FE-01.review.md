Checks I ran myself: `flutter analyze` found 0 issues and `flutter test` passed 91 of 91 (logs: build/fe01-review-analyze.log and build/fe01-review-test.log). Apart from `test/support/fake_backend.dart`, which the rules allow to change, no baseline test file was edited.

## Medium

### M1. The row selection survives a change of view scope, so bulk actions and exports act on rows that are no longer shown
- Where: `frontend/lib/core/table/table_providers.dart:62,71` and `frontend/lib/core/table/data_table_scaffold.dart:139-152,473-505`.
- FE-01 makes `tablePageProvider` and `tableSummaryProvider` watch `viewScopeProvider`. When the scope changes, the list now reloads for different regions or a different date without its `query` changing.
- `DataTableScaffold` clears `_selected` and `_selectAllMatching` only in `didUpdateWidget` when `oldWidget.query != widget.query`, or in `_refresh`. It does not watch the scope.
- Failure scenario:
  1. A user ticks three invoices in NORTH while viewing NORTH and SOUTH.
  2. They switch the scope to SOUTH only. The table reloads and shows SOUTH rows.
  3. The toolbar still says "3 selected".
  4. Bulk (`'ids': _selected.toList()`, line 475) and export (line 501) send the three NORTH ids.
- By I3, explicit ids are authorised against each record's own region, not narrowed by `regionIds`. So the action runs on, or exports, records outside the chosen regions.
- The same happens when switching between live and historical views.
- No slice in §9.2 covers this (DESIGN.md never mentions clearing the selection). FE-01 is the slice that makes it reachable; the region selector that exposes it arrives in FE-02.
- Fix: clear the selection when the scope changes. For example, in `DataTableScaffold` add `ref.listen(viewScopeProvider, (_, __) => _clearSelection())` in build, and name this in FE-02's list, with a test in `region_selector_test`.

## Low

### L1. No test proves that the production `dioProvider` installs the scope interceptor
- Where: `frontend/lib/core/api/api_client.dart:27`.
- Every test that uses `dioProvider` overrides it (`grep -rn dioProvider test | grep -v overrideWith` finds nothing). The one test that uses the real provider (`view_scope_test.dart`, "on sign out") makes no request.
- Deleting line 27, or placing it after the auth interceptor, would leave all 91 tests green. This line is the only production carrier of `regionIds` and `asOf`, which is critic risk R1 (dropped parameters), and R1 is mapped to FE-01.
- Fix: add a test that reads `dioProvider` with `tokenStorageProvider` overridden, checks that `dio.interceptors` contains the scope interceptor ahead of the auth interceptor, or replaces the adapter with a recording `HttpClientAdapter` and asserts the query parameters sent.

### L2. `CurrentUser.hasIn` answers false for a global privilege the user holds
- Where: `frontend/lib/shared/models/auth_models.dart:88-94`.
- This follows the letter of §7.2, but `regions[].privileges` lists only regional privileges (§6.2). So `hasIn(Privileges.automationManage, 2)` is false even for an ADMIN, which contradicts the effective-right formula in §4.2, where `global(p)` alone is enough.
- It is latent: nothing calls it yet, and the implementer recorded it as a gap. But FE-03 and FE-07 gate create flows with `hasIn`, and the helper silently denies global rights.
- Fix: fall back to `has(p)` for the 13 global names, for example with a `Privileges.global` set mirrored from §4.1.

## Checked and fine
- `ViewScope.apiParams`: only what is set; ids as one sorted string; `DateFormat('yyyy-MM-dd')` on the local date; `==` and `hashCode` over the canonical string.
- `viewScopeInterceptor`: uses `putIfAbsent`, runs on every method, and reads the scope when each request goes out.
- Nothing is put into `TableRequest.extra`.
- `checkAsOf`: the matching date gives historical, `live` gives live, a missing or different header throws.
- `historyRangeProvider` is autoDispose and nothing reads it at build.
- The scope is cleared on logout (explicitly; the test does not rely on the listener) and when the signed-in user id changes.
- `PagedResult` gains `regionIds`, `bookRegionIds` and `asOf`, parsed tolerantly and copied by `map`.
- `RegionAccess` and `CurrentUser.regions` default to `const []`.
- There are nine privilege constants, spelled as the backend spells them.
- `NavBadge` is in place, and Inbox uses `inbox`.
- `FakeReply` and `dioWith` behave as specified. `Headers.fromMap` lower-cases keys, so `x-view-as-of` lookups work.
- There is no provider cycle: the interceptor first reads `viewScopeProvider` from inside Dio's asynchronous interceptor chain, not during a provider build.
